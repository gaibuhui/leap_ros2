## 终端分工（先看这个）

后面每一步都会标出**该在哪个终端里执行**。终端名是固定的，请照此对号入座，
**不要在一个终端里混着干两件事**（尤其是 A 和 E，混用必出错）。

| 终端 | 名字 | 干什么 | 命令 | 生命周期 |
|---|---|---|---|---|
| **A** | 链路（常驻） | micro-ROS Agent + 机器人模型/TF | `bash 05_run_robot.sh core` | **从头开到关机，全程不关** |
| **B** | 检查与诊断 | 看话题、看会话状态、改机器人配置、一键复位 | `bash 05_run_robot.sh topics` / `reset`、`bash 09_preflight.sh`、`ros2 topic hz/echo/pub` | 随手开，用完可关 |
| **C** | 遥控 | 键盘开小车 | `ros2 run teleop_twist_keyboard teleop_twist_keyboard` | 开第 6 步时开 |
| **D** | 建图 / 导航 / RViz | SLAM、Nav2、rviz2、Qt 面板 | `bash 05_run_robot.sh slam` / `nav-rviz` / `rviz` / `qtgui` | 开第 7 步时开（可开多个） |
| **E** | 固件烧录 | ESP-IDF 编译烧录（**绝不 source ROS**） | `bash 04_flash_firmware.sh low` / `cam`、`sudo bash 11_fix_serial_perm.sh` | 只在第 2 步用，用完就关 |

**三条铁律：**

1. **终端 A 全程别关**。它一关，Agent 就停了，机器人跟着掉线，而且**不会自动重连**（见 4.2）。
   > ⚠️ 真要关终端 A 时，**在终端里按 `Ctrl+C`**，别用窗口右上角的 ✕ 直接叉掉。
   > 叉窗口的话 Agent 不会退出，会变成占着 8888 端口的「孤儿进程」，
   > 下次 `core` 就报 `UDP :8888 已被占用`（处理见 4.2 或 README 的 Q23）。
2. **终端 E 里不要 source ROS 2**。ROS 2 和 ESP-IDF 都改 `PYTHONPATH`，同终端混用必崩（见 2.2）。
3. **每个终端开好先确认自己在哪个终端**：终端标题/标签上写一下名字，或执行 `pwd` 看看当前目录。

> 终端 B 的每条命令都是独立的，**新开一个窗口执行完就可以关掉**，不影响 A。
> 只有 A（以及第 6/7 步的 C、D）是需要"一直挂着"的。

## 第 0 步 · 先搞懂你要连的是什么

**整套系统只有两台"电脑"：**

| 角色 | 是什么 | 干什么 |
|---|---|---|
| **机器人（下位机）** | 车上的两块 ESP32-S3 板子 | 读传感器、控电机、发数据 |
| **上位机（你的电脑）** | 装了 Ubuntu + ROS 2 的 Linux 主机 | 收数据、算算法、发指令 |

**两块板子分工**（很多人搞混，先记住）：

| 板子 | 固件工程 | 职责 |
|---|---|---|
| **主控板**（带电机接口、雷达接口） | `~/leap_firmware/leap_low_v1` | 电机控制、里程计、IMU、**激光雷达**、电池、超声波 |
| **图传板**（带摄像头排线） | `~/leap_firmware/leap_cam` | 摄像头 MJPEG 视频流、WiFi 配网门户 |

**数据是怎么从车上到电脑的**（这条链路理解透，后面所有问题都能自己定位）：

```
   ┌─────────────── 机器人 ───────────────┐
   │  主控板 (ESP32-S3)                    │
   │   ├─ 激光雷达  ──UART1(GPIO41)──┐     │
   │   ├─ IMU / 电池 / 超声波 ───────┤     │
   │   └─ 电机编码器 ────────────────┤     │
   │                                 ↓     │
   │                          micro-ROS 协议│
   └───────────────────────────────────────┘
                          │
              UDP :8888   │   （双向：车上发状态，电脑发指令）
                          ↓
   ┌─────────────── 上位机 (你的电脑) ──────┐
   │  micro_ros_agent  ← 把 UDP 转成 ROS 2  │
   │        ↓                              │
   │  ROS 2 话题: /scan /odom /imu ...      │
   │        ↑                              │
   │  发 /cmd_vel  → 回传到车上 → 电机转     │
   └───────────────────────────────────────┘

   摄像头是独立的一条线（走 HTTP，不是 ROS）：
   图传板 ──HTTP :81 MJPEG──→ 浏览器 / camera 节点
```

> **关键认知**：激光雷达**不是插在你电脑上的**。它插在机器人主控板上，主控把雷达数据打包成 ROS 的 `/scan` 话题，通过 WiFi 传给你。所以电脑上**不需要**接任何雷达 USB 线。

## 第 1 步 · 接线与上电

### 1.1 认识接口

**主控板**（对照板子丝印）：

| 接口 | 接什么 |
|---|---|
| `M1 / M2`（6P 白色座） | 左、右电机 |
| 4P 座（标 `LIDAR` 或雷达图样） | 激光雷达 |
| Type-C | 烧录 / 供电 / 调试串口 |
| 电池座（`BAT`） | 2S~3S 锂电池 |

**图传板：**

| 接口 | 接什么 |
|---|---|
| 24P FPC 排线座 | 摄像头模组 |
| Type-C | 烧录 / 调试 |
| 4P 座 | 连到主控（供电 + 串口通信） |

### 1.2 接线顺序（**先别插电池！**）

```
① 电机线        → 主控 M1 / M2
② 激光雷达线    → 主控雷达座（注意卡扣方向，别硬插）
③ 图传板排线    → 摄像头（金手指朝下，压紧扣好）
④ 图传板 4P 线  → 主控对应座
⑤ 最后再插电池
```

> ⚠️ **一定要最后插电池。** 先接负载后通电是基本习惯；如果某根线短路，先插电池会直接烧板子。

### 1.3 上电自检

插上电池（或拨开关 ON）后观察**主控板上的两个灯** —— 它们是两个独立的灯，别混为一谈：

| 灯 | 电路（原理图） | 谁控制 | 含义 |
|---|---|---|---|
| **电源指示灯** | `3V3 → R23 5.1kΩ → LED → GND` | **硬件直连，固件管不了** | **常亮 = 供电正常**。它永远不闪 |
| **状态灯 LED1** | 白色 0603（`KT-0603W`），`GPIO14 → R1 5.1kΩ → LED1` | 固件 `status_led` | 见下表 |

**状态灯（白灯）语义**（源码 `components/status_led/status_led.cpp`，`active_high`）：

| 现象 | 翻转周期 | 代码 | 含义 |
|---|---|---|---|
| 灭 | — | `kOff` | 没上电 / 还没跑到初始化 |
| **常亮** | — | `kOn` | **已连上 WiFi**（STA 成功）→ 可以进第 4 步 |
| **快闪**（很急促，每秒约 4 次） | 120 ms | `kFastBlink` | **没连上 WiFi → 已开配网热点等你配网**（正常，第 3 步处理） |
| **慢闪**（一秒 1 次） | 500 ms | `kSlowBlink` | 你按过 BOOT 键，模式被切到 **micro-ROS** |

> **一句话判据：白灯在闪 = 还没连上 WiFi；白灯常亮 = 已经连上了。**

上电后的完整流程（`app_runtime.cpp` + `wifi_app.cpp`）：

```
上电
 ├─ 白灯常亮（初始化完成）
 ├─ 尝试连已保存的 WiFi
 │   （没保存过凭据时，会试作者的默认：SSID=Maturo / 密码=maturo2026）
 ├─ 等 15 秒（kWifiConnectTimeoutMs）
 │
 ├─ 连上  →  白灯保持【常亮】，启动通信任务
 └─ 超时  →  开配网热点 Maturo_<MAC> + 白灯【快闪】
```

其它现象：

| 现象 | 含义 |
|---|---|
| 图传板 LED 亮 | 图传板已上电 |
| 两个灯都不亮 | 检查电池电压（≥ 7.4V）、开关、排线 |

> ⚠️ **BOOT 键（GPIO0）短按 = 切换通信模式**：按住 50~1200ms 松开即切换，
> 切向 micro-ROS → 白灯**慢闪**；切回 MAVLink → 白灯**常亮**。跑 ROS 2 需要 micro-ROS 模式。
> 注意 GPIO0 是 strapping 脚，**上电瞬间按住会进下载模式**，别乱按。
>
> 🔎 **灯判断不了通信模式**：STA 一连上，白灯就是常亮，不管当前是 micro-ROS 还是 MAVLink。
> 只有"按 BOOT 切换的那一下"才会用慢闪/常亮区分。要确认模式请看配置页或串口日志。

## 第 2 步 · 烧录固件

> **如果卖家已经帮你烧好了固件，可以跳过这一步**，直接到第 3 步。
> 判断方法：上电后能用手机搜到 `Maturo_xxxxxx` 开头的 WiFi 热点，说明固件已烧。

### 2.1 准备工作

> 🖥️ **本节所有命令都在【终端 E · 固件烧录】里执行。**
> 这个终端**不要** source ROS 2（`/opt/ros/humble/setup.bash`），否则 ESP-IDF 会加载失败（原因见 2.2）。

用 Type-C 数据线把**主控板**接到电脑（注意必须是**数据线**，不能是只有充电功能的线）。

```bash
# 【终端 E】查看是否识别到串口
ls /dev/ttyUSB* /dev/ttyACM*
```

应该出现 `/dev/ttyUSB0` 或 `/dev/ttyACM0`。如果没有：
- 换一根线、换一个 USB 口
- 检查是否已加入 dialout 组：`groups | grep dialout`

**⚠️ 看到串口 ≠ 能用！还要确认权限（这一步最容易卡）：**

```bash
# 【终端 E】
ls -l /dev/ttyUSB0
# 期望：crw-rw-rw-  ...  ✅
# 若显示：crw-rw---- root dialout 660   ❌ 当前用户打不开，烧录必然失败
```

不动手查也行 —— 在【终端 B】跑 `bash 09_preflight.sh`，它的「2. 串口设备」一节会直接告诉你。

**权限不对时**（两种常见原因），都在【终端 E】修复：

| 原因 | 修复 |
|---|---|
| **udev 规则没匹配到芯片**<br>（CH340 实际是 `1a86:7522`，规则却写死了 `7523`） | `sudo bash 11_fix_serial_perm.sh`（一键修复，会重写规则并重新应用） |
| **已在 dialout 组，但当前终端是加组之前开的** | `newgrp dialout`（仅本终端生效）<br>或**注销后重新登录**（永久生效） |

> 确认芯片型号：`udevadm info -q property -n /dev/ttyUSB0 | grep -E 'VENDOR_ID|MODEL_ID'`
> 国产 ESP32 开发板多为 CH340（`1a86:75xx`），少数 P 版用 CP210x（`10c4:ea60`）。

### 2.2 烧录主控固件

```bash
# 【终端 E · 固件烧录】
cd /media/lixin/新加卷/robot/setup
bash 04_flash_firmware.sh low          # 烧主控固件
```

脚本会**在编译前先检查串口权限**（失败立即报错，不用等编译完几分钟）。

脚本会自动：确定串口 → 检查权限 → 编译（如未编译）→ 烧录 → 打开监视器。

**⚠️ 如果你看到它只打印了 `==> 1/5 加载 ESP-IDF 环境` 就退回提示符**（没有任何报错），
那不是"没反应"，是脚本被环境搞崩了。

**原因**：你的 `~/.bashrc` 里 source 了 ROS 2（`source /opt/ros/humble/setup.bash`），
它会让 `PATH` 上的 `python3` 变成 `/usr/bin/python3`（3.10），
于是 ESP-IDF 去找 `~/.espressif/python_env/idf5.5_py3.10_env`，
而工具链实际装的是 `idf5.5_py3.13_env` → 找不到 → `export.sh` 内部失败 →
在 `set -e` 下一句话不说就退出。**ROS 2 和 ESP-IDF 都改 `PYTHONPATH`，天生冲突。**

**已经修好了**：`04_flash_firmware.sh` 现在会自己清理 ROS 的污染变量、
并显式指定已安装的 python 虚拟环境，**你不需要先 `get_idf`，直接跑就行**。

如果你需要**交互式**用 `idf.py`（不是烧录），重跑一次安装脚本会给你一个带环境清理的 `get_idf` 函数：

```bash
# 【终端 E】
bash 03_install_espidf.sh     # 幂等：已装的会跳过下载，只补配置
```

看到类似输出即成功：
```
Hash of data verified.
Leaving...
Hard resetting via RTS pin...
```

### 2.3 烧录图传固件

拔掉主控的线，把图传板接到电脑，然后：

```bash
# 【终端 E】
bash 04_flash_firmware.sh cam          # 烧图传固件
```

> **一块一块烧！** 两块板同时插着会分不清是哪个串口，容易烧错。

### 2.4 烧录后验证

```bash
# 【终端 E 或 B 都行】拔掉数据线，给机器人上电，等 10 秒
# 然后用手机搜 WiFi，应该能看到这样的热点：
#   Maturo_A1B2C3D4E5F6      ← 主控的配网热点
```

搜到了 → 固件正常，进第 3 步。

## 第 3 步 · 配网（最容易卡住的一步）

机器人和你的电脑必须在**同一个 WiFi 网络**下才能通信。配网就是告诉机器人："连哪个 WiFi、电脑的 IP 是多少"。

### 3.1 先查你自己电脑的 IP

```bash
# 【终端 B · 检查与诊断】
cd /media/lixin/新加卷/robot/setup
bash 09_preflight.sh
```

看第 2 节输出，例如：

```
     wlp3s0  [WiFi]  192.168.1.23
     enp2s0  [有线/其他]  192.168.1.24

  >>> 把下面这个 IP 填到机器人配网页的 "micro-ROS Agent IP" 里：
        192.168.1.23
```

**📌 记下这个 IP（下面称它 `<电脑IP>`），第 3.4 步要用。**

> 建议：**电脑用网线连路由器**，比 WiFi 稳定得多，丢包少。此时用有线网卡的 IP。

### 3.2 连接机器人的配网热点（⚠️ 先分清是哪块板子）

机器人上有 **两块 ESP32-S3 板子**，**各自都会发一个 `Maturo_` 开头的热点**，
它们的配网页地址 **完全不同**：

| 板子 | 作用 | 热点名称 | 配网页地址 |
|---|---|---|---|
| **主控板** `leap_low_v1` | 电机/IMU/雷达/micro-ROS | `Maturo_<12位MAC>` | **`http://192.168.4.1`** |
| **图传板** `leap_cam` | WiFi 图传摄像头 | `Maturo_CAM_<12位MAC>` | **`http://192.168.1.88`** |

**判别方法：名字里带 `CAM` 的是图传板，不带的是主控板。**

- 要**跑 ROS 小车** → 必须连 **主控板**（不带 `CAM`）那个热点，地址 `192.168.4.1`
- 只想**看摄像头画面** → 连 **图传板**（带 `CAM`）那个热点，地址 `192.168.1.88`

> ❗**最常见的坑**：连了 `Maturo_CAM_xxxxxx`（图传板），却去开 `192.168.4.1`。
> 此时浏览器会报 **"服务器响应时间过长 / 无法访问此网站"** —— 因为 `192.168.4.1`
> 根本不在当前网段里，请求被丢给默认路由（有线网卡）发到外网去了，必然超时。
> **这不是故障，是连错热点了。**

**操作步骤：**

1. 打开 WiFi 列表
2. **只连一个** `Maturo_` 热点 —— 无密码，直接连（一次别同时连两个）
3. 连上后系统一般会自动弹出配网页面；没弹出就看 3.3

### 3.3 打开配网页

**先确认你连的是哪个热点，再用对应的地址：**

```bash
# 【终端 B】不确定连的是哪块板，跑这个，它自动判别该开哪个网址
bash 10_diag_portal.sh
```

| 你连的热点 | 浏览器打开 |
|---|---|
| `Maturo_<12位MAC>`（主控板） | **`http://192.168.4.1`** |
| `Maturo_CAM_<12位MAC>`（图传板） | **`http://192.168.1.88`** |

> 注意：主控板是 `192.168.4.1`，**不是** `192.168.1.1`，也**不是** `192.168.1.88`。
> 如果你连的是图传板却开 `192.168.4.1`，请回 3.2 换热点。

### 3.4 填写配置（**这一步填错，后面全都不通**）

页面上需要填三块内容：

| 字段 | 填什么 | 说明 |
|---|---|---|
| **WiFi 名称** | 你家/实验室路由器的 WiFi 名 | 机器人要连的这个 |
| **WiFi 密码** | 对应密码 | |
| **micro-ROS Agent IP** | **`<电脑IP>`**（第 3.1 步查到的） | ❗最容易填错的一项 |
| **通信模式** | 选 `micro_ros` | 我们用的就是 micro-ROS |
| 端口 | `8888` | 保持默认 |

**填写要点：**

- **Agent IP 是"你电脑的 IP"**，不是路由器的 IP（`192.168.x.1`），不是机器人的 IP。
- 页面上如果显示 `192.168.31.214`，那是**原作者的电脑 IP**，必须改成你的。
- 电脑 IP 之后可能变（路由器重新分配 DHCP）。如果哪天连不上了，**先回来重新确认这个 IP**。

### 3.5 保存并等待重启

点击保存后：
1. 机器人会重启并连接你指定的 WiFi
2. 主控 LED 从**快闪变为慢闪**（或常亮）→ 说明连上了
3. 配网热点 `Maturo_xxxxxx` 会消失

### 3.6 验证机器人真的上网了

**最快的办法是看灯**（不用连网、不用工具）：

| 主控板状态灯（白灯） | 结论 |
|---|---|
| 还在**快闪** + 热点 `Maturo_xxxx` 还能搜到 | ❌ 没配成功，回 3.4 重填 |
| **常亮**（不闪了）+ 热点消失 | ✅ 已连上你的路由器 |

再用命令交叉验证：

```bash
# 【终端 B】更直接的办法：扫描局域网设备
ip neigh | grep -i "192.168"      # 列出已知的局域网邻居
```

**如果机器人没连上**（热点一直不消失）：
- WiFi 名字/密码填错 → 重新连热点配一遍
- 路由器开了 **AP 隔离**（无线设备之间不能互访）→ 关掉它
- 路由器只支持 5GHz → ESP32 **只支持 2.4GHz**，必须有 2.4G 频段

> ⚠️ **ESP32 只认 2.4GHz WiFi。** 如果你的路由器把 2.4G 和 5G 合并成一个名字（双频合一），可能会连接失败。建议在路由器里把 2.4GHz 单独设一个 SSID，让机器人连那个。

### 3.7 ★ 不连热点也能读状态 / 改配置（实测有效，强烈推荐）

**主控板连上 WiFi 后，配网页依然开着**（STA 模式下 TCP 80 仍在监听）。
所以只要机器人已经联网，**不需要断开当前 WiFi 去连它的热点**，
直接用 HTTP 就能读状态、改配置：

```bash
# 【终端 B】以下三条依次执行
# 1) 找到机器人 IP（09_preflight.sh 会自动扫出来）
bash 09_preflight.sh

# 2) 直接读它的完整状态（JSON）
curl -s http://<机器人IP>/api/status | python3 -m json.tool

# 3) 直接改 Agent IP —— 不用连热点、不用开浏览器（会触发机器人重启）
curl -X POST http://<机器人IP>/api/runtime-config \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'comm_mode=micro_ros&microros_agent_ip=<你的电脑IP>&microros_agent_port=8888'
# 返回 {"ok":true,"restart":true} → 机器人自动重启，约 10 秒后重连
```

> 💡 **懒人版**：改 Agent IP + 复位机器人，一条命令搞定（会自动扫出机器人、自动填本机 IP）：
> ```bash
> # 【终端 B】
> bash 05_run_robot.sh reset
> ```

**什么时候用得上**：

- 电脑 IP 变了（换网络 / 路由器重新分配 DHCP），要改 Agent IP
- **主控板热点根本连不上**（信号弱、被同频干扰、网卡关联被踢）——
  这时"连热点配网"这条路走不通，但走 HTTP 完全没问题，因为机器人已经在局域网里了
- 想确认机器人到底连上没有、雷达有没有数据、电量多少

**固件提供的全部 API**（源码 `wifi_provision_task.cpp` 注册表，工整可查）：

| 端点 | 方法 | 作用 |
|---|---|---|
| `/` | GET | 配网页 HTML |
| `/api/status` | GET | 完整状态 JSON（WiFi / 电量 / IMU / 雷达 / micro-ROS 配置）|
| `/api/scan` | GET | 扫描周围 WiFi |
| `/api/provision` | POST | 配网（`ssid` / `password`）|
| `/api/runtime-config` | POST | 改通信模式与 Agent（`comm_mode` / `microros_agent_ip` / `microros_agent_port`）|
| `/api/camera/provision` | POST | 给图传板下发 WiFi 配置 |

> 💡 `/api/status` 是**排查神器**，一眼看出：
> `sta_connected`（连上没有）、`rssi`（信号）、`lidar.valid_points`（雷达有无数据）、
> `microros_agent_ip`（配没配对）、`battery.percentage`、`temperature.celsius`。
>
> 实测样例（机器人正常联网时）：
> ```json
> {"wifi":{"sta_connected":true,"ssid":"lx","rssi":-23,"channel":11},
>  "runtime":{"comm_mode":"micro_ros","microros_agent_ip":"10.182.70.36","microros_agent_port":8888},
>  "lidar":{"valid":true,"valid_points":233},"battery":{"percentage":53,"voltage_v":7.277}}
> ```

**启动后 12 秒内，脚本会自己判断机器人连上没：**

| 你看到的 | 含义 | 下一步 |
|---|---|---|
| `[ OK ] 机器人已连接 —— Agent 会话已建立` | 链路通了 | 直接进第 5 步 |
| `[WARN] 机器人还没连上 Agent` | 机器人没来找 Agent | **按一下主控板的 RESET 键**；或在【终端 B】执行 `bash 05_run_robot.sh reset`。<br>本命令**继续跑着不用重启**，连上后话题会自动出现 |

**⚠️ 这就是最常见的卡点：Agent 比机器人晚起（或 Agent 重启过/换过端口）时，机器人不会自己重连，必须复位一次。**

**为什么必须这样做**（源码级原因）：

固件里一旦连接建立，`rcl_wait` 的**超时被当作"正常"**返回
—— `microros_task.cpp` 里的 `spin_once()`：

```c
ret = rcl_wait(&s_wait_set, RCL_MS_TO_NS(timeout_ms));
if (ret == RCL_RET_TIMEOUT) {
    return true;        // ← 超时也返回 true，于是永远不触发重建
}
```

结果就是 `s_ros_created` 一直为真 → **机器人再也不会去 `ping` Agent**。
所以 **Agent 比机器人晚起时，它自己永远连不上**，只能靠重启机器人重新握手。

> **实测对照**：
> - 机器人刚重启时起 Agent → **2 秒内** `session established` ✅
> - 机器人已跑了 100 多秒时起 Agent → 30 秒毫无反应 ❌，**复位后立刻连上** ✅

**⚠️ 如果启动时先报了 `UDP :8888 已被占用`：**

说明**上一次的 Agent 还在**。分两种情况：

| 情况 | 怎么认 | 怎么办 |
|---|---|---|
| 上一个【终端 A】还开着 | 那个终端还能看到输出 | 去那个终端按 `Ctrl+C`，再重跑 `core` |
| 那个终端已被**直接叉掉**（孤儿进程） | 找不到那个终端，`Ctrl+C` 无处可按 | 用 `bash 05_run_robot.sh core --force` 自动清理；或按提示 `kill <PID>` |

> 终端被叉掉时，里面的 Agent **不会退出**，会改挂到 `systemd` 名下继续占着 8888
> （实测残留过 24 分钟）。脚本现在会直接告诉你占用者的 PID、运行时长和"是否孤儿"。
>
> **清掉旧 Agent 后，机器人会话也断了**，所以接下来**仍要复位机器人**
> （按 RESET 键，或【终端 B】`bash 05_run_robot.sh reset`）。

**【终端 A】的正常输出长这样：**

#### 4.2.1 想让它转弯更稳？把 `core` 换成 `ekf`

**先照上面的 `core` 跑通整条链路，再考虑这一步。** 它不是必须的。

问题：固件的里程计偏航是**纯轮速差积分**（`odom_yaw_ += local_vw * dt`），
轮子一打滑、或者轮距不准（固件 150 mm vs URDF 200 mm），**一转弯方向就偏**，
建图时墙角会被"扭"成弧线。而固件其实已经把 IMU 偏航算好了，只是从没喂进里程计。

```bash
# 【终端 A · 用这个替代 core】
bash 05_run_robot.sh ekf
```

它比 `core` 多做了两件事：把 IMU 的**角速度**融进里程计（陀螺比轮速差分可靠得多），
并把 `odom→base_footprint` 这条 TF 交给 EKF 独占（自动给底盘传 `publish_tf:=false`）。

**你不需要自己改任何文件**，但要知道三件事：

1. 固件发的 IMU 协方差是 `-1`（=无效），robot_localization 会**直接丢弃**。
   脚本会自动起一个修正节点把它补好，转发到 `/imu/data` —— **不用重烧固件**。
2. **同一条 TF 只能有一个发布者**。所以 `ekf` 模式下底盘不再发那条 TF；
   如果你手动分步启动，记得 `publish_tf:=false`。
3. 启动 EKF 后**里程计会归零**（以启动那一刻为原点），这是正常行为，
   对建图和导航没有影响。

**验证：**

```bash
# 【终端 B】EKF 应该在 30 Hz 输出
ros2 topic hz /odometry/filtered

# 协方差应该不再是 -1
ros2 topic echo /imu/data --once | grep -A4 covariance
```

> 完整原理、改了哪些文件、怎么回退，见 README **Q29**。

会生成 `~/my_map.pgm` 和 `~/my_map.yaml`。

> ⚠️ **`Fixed Frame` 要和当前阶段匹配**：
> 跑 SLAM / 导航时用 **`map`**（项目配置里就是 `map`）；
> 如果**只起了核心链路、没跑 SLAM**，`map` 这个坐标系还不存在，
> 整片 3D 区会变成空的 → 这时改成 **`odom`** 或 **`base_footprint`**。

**⑤ 建图时地图/扫描在「抖动」，但车明明没动？**

先**一条命令定性**（车必须静止）：

```bash
# 【终端 B】
bash 12_diag_jitter.sh
```

它会把抖动分成三层量出来，并直接给结论：

| 层 | 怎么读结果 | 说明 |
|---|---|---|
| **里程计** | `odom→base_footprint` 的偏航峰峰值 | 静止时 >1° 就说明里程计本身在抖 |
| **gmapping** | `map→odom` 的偏航峰峰值 | 静止时应该几乎为 0；会变说明修正在跳 |
| **雷达数据** | `/scan` 零值比例、最长连续零段 | 零值 >20% 就说明有整段角度收不到回波 |

**原理一句话**：RViz 用 `Fixed Frame = map` 显示时，机器人的位置 = `map→odom` × `odom→base_footprint`。
gmapping **只在车移动 1 m、转 0.5 rad 或每 1 秒**时才重算一次 `map→odom`，
所以这中间**里程计的所有噪声都会直接画到屏幕上**，360° 的扫描随之来回摆 → 看着就是放射状「辐条」。

> ⚠️ **重要坑**：`params/slam_gmapping.yaml` 是**死配置** —— 这个包的源码里**一处都没有读参数**，
> 所有参数都硬编码在 `slam_gmapping.cpp` 的 `init()` 里。
> 所以**改 YAML 里的 `maxRange` / `maxUrange` / `linearUpdate` 完全无效**，必须改源码再 `colcon build`。
> 详见 `README.md` 的 **Q25**。

**⑥ 点了 `2D Pose Estimate` 之后，地图突然开始抖？**

**因为你把两套定位同时跑起来了。**

| | 说明 |
|---|---|
| `2D Pose Estimate` 按钮发的 | `/initialpose`（发布者是 `rviz2`，Qt 面板的"设定初始位姿"也发这个） |
| gmapping | **不订阅** `/initialpose`（源码里**根本没有**）→ 建图时点它**完全没用** |
| amcl（Nav2 的定位） | **订阅** `/initialpose`；收到后**才开始广播 `map→odom`** |

所以只要 Nav2 的 amcl 处于 `active` 状态，你一点这个按钮就等于**把 amcl 叫醒了**：
它立刻开始发 `map→odom` —— 而 **gmapping 也在发同一条 TF 边**。

实测（车静止、两套同时跑，抓 6 秒 `/tf`）：

```
map→odom 只在两组固定值之间交替：
    x = -1.1551  (gmapping)   ←→   x = +0.0566  (amcl)
相邻帧 x 跳变 >5cm 的次数 = 77/148，最大跳 121 cm；yaw 最大跳 27°
```

**判据**：`map→odom` 只在**两组固定值之间来回横跳**、而车是静止的 —— 这就是两个广播者的签名。
（噪声不长这样：噪声会是很多个分散的值。`12_diag_jitter.sh` 的第 0b、2 节会自动判定。）

**解决**：只留一套。建图阶段关掉 Nav2；导航阶段先关掉 SLAM。详见 7.2 的警告框。

### 7.2 导航（Nav2）

> ### ⛔ 先记住这条：导航前**必须关掉 gmapping（SLAM）**
>
> **SLAM 和 Nav2 的 amcl 是互斥的两套定位方案**，两者都会广播 `map→odom`、
> 也都会往 `/map` 发地图。同时跑的话：
>
> - RViz 每帧随机取其中一条 TF → **地图原地剧烈抖动、车位置乱跳**
> - **尤其在你点了 `2D Pose Estimate` 之后会突然开始抖** —— 这个按钮发的是
>   `/initialpose`，而 **gmapping 源码里根本没有订阅它**，是 **amcl** 收到后才
>   开始发 `map→odom`，两条 TF 从这一刻打起来。
>
> 正确顺序：
> ```bash
> # ① 建图阶段：只跑 SLAM
> bash 05_run_robot.sh slam
> # ② 地图保存后：在 SLAM 那个终端按 Ctrl+C 关掉它
> # ③ 再起导航
> bash 05_run_robot.sh nav-rviz
> ```
> 脚本现在会在 `slam` / `nav` / `nav-rviz` 启动前自动检测并拦截（`topics` 可随时查）。
> 抖动诊断：`bash 12_diag_jitter.sh`（第 0b 节专门查这个）。

```bash
# 【终端 D】先确认 SLAM 已关，再执行
bash 05_run_robot.sh nav-rviz      # 启动导航 + RViz
```

**操作流程：**
1. RViz 里点 `2D Pose Estimate`，在地图上点出**车当前的实际位置和朝向**
   （**这一步只有在 Nav2/amcl 下才有意义**；建图时点它没用，只会把 amcl 唤醒去抢 TF）
2. 点 `Nav2 Goal`（或 `2D Goal Pose`），在地图上点**目标点**
3. 车会自己规划路径、避障、开过去

> 导航对**里程计精度**和**地图质量**很敏感。如果车走偏，多半是：
> - 建图时开太快（雷达运动畸变大）
> - 轮子打滑（里程计漂移）
> - 地图和实际环境对不上

**注意**：`nav` / `nav-rviz` 默认加载的是作者示例地图
（`xuegecar_navigation2/maps/room.yaml`）。要导航你自己的房间，先保存地图
（见 7.1 第 4 步的 `map_saver_cli`），再指定：

```bash
# 【终端 D】用自己保存的地图启动
ros2 launch xuegecar_navigation2 navigation2_rviz.launch.py map:=$HOME/my_map.yaml
```

## 第 8 步 · 看摄像头画面

摄像头有**三条路**可以看，先搞清楚区别，出问题时才不会查错方向：

| 看的地方 | 走什么通道 | 前提条件 |
|---|---|---|
| 浏览器 | 直连图传板 MJPEG | 什么都不需要，图传板自己就在推流 |
| **Qt 面板**「摄像头画面」 | ROS 话题 `/camera/image_raw/compressed` | **必须跑 `http_video_publisher` 节点** |
| RViz | ROS 话题（Image 显示） | 同上 |

> ⚠️ 最容易困惑的一件事：**浏览器能看到画面，不代表 Qt 能看到。**
> 浏览器**完全不经过 ROS**；而 Qt 订阅的是 ROS 话题，需要一个节点把 MJPEG
> 转成 ROS 消息。这个节点没跑，Qt 就会一直停在 `等待 /camera/image_raw/compressed`。
> 详见 README **Q28**。

**在 Qt 面板里看（最省事）：**

```bash
# 【终端 E】
bash 05_run_robot.sh qtgui
# 面板启动 1.5 秒后会自动拉起相机节点
# （面板底部有开关「启动面板时自动打开摄像头」，不需要时可以取消勾选）
```

**约 8~10 秒后**画面出现 —— 相机要预热，别急着判定坏了。

**在浏览器里看（验证"相机本身好不好"最快的办法）：**

摄像头走的是**独立的 HTTP 流**，最简单的方式是直接用浏览器看。

**⚠️ 先分清两种状态下的地址，别混：**

| 状态 | 地址 | 什么时候用 |
|---|---|---|
| 图传板 **AP 模式**（还没配网） | `http://192.168.1.88/`（配网页）<br>`http://192.168.1.88:81/`（图传流） | 首次配网时，电脑直连 `Maturo_CAM_*` 热点 |
| 图传板 **已连上路由器**（STA 模式） | `http://<路由器分给它的IP>:81/` | 正常跑车时，电脑和图传板在同一路由器下 |

```bash
# 【终端 B】已配网后，不用去翻路由器后台 —— 直接跑预检，它会问机器人要地址
bash 09_preflight.sh
# 第 6 节会打印：相机地址 : http://192.168.1.102:81/（机器人上报的实际值）
```

> 注意：`192.168.1.88` 只在**直连图传板热点**时才是它；
> 一旦图传板连上你家的路由器，它的地址就变成路由器 DHCP 分的那个了
> （主控的 `/api/status` 里一直带着这个地址，所以能自动问出来）。

**✅ 现在不用手改 IP 了** —— `cam` 模式会**直接问主控板要图传板的真实地址**
（主控的 `/api/status` 里带 `camera.stream_url`），再通过 launch 参数传进去：

```bash
# 【终端 D】地址自动发现，不用改任何文件
bash 05_run_robot.sh cam
# 日志会打印：
#   [INFO] 从机器人 192.168.1.103 自动发现相机：http://192.168.1.102:81/
```

想手动指定也可以：

```bash
# 【终端 D】
bash 05_run_robot.sh cam http://192.168.1.102:81/
```

**验证：**

```bash
# 【终端 B】
ros2 topic hz /camera/image_raw/compressed
```

> ⚠️ **相机要预热：从发起连接到出第一帧需要 8~10 秒。**
> 所以用 `curl http://<相机IP>:81/` 手测时，**前 8 秒完全没响应**（连 HTTP 头都不发），
> 短超时会误判成"流坏了"。实测 20 秒能收 9.3 MB ≈ 14 fps，每帧约 32 KB。

**如果偏要走 `ros2 launch` 而不走脚本**，那就得改配置文件里的默认值：

```bash
# 【终端 B】
grep -n url ~/leap_ros_ws/src/xuegecar_camera/config/http_video_publisher.yaml
# 当前已设为 http://192.168.1.102:81/（原为作者默认 192.168.31.185）
# workspace 是 --symlink-install 建的，改完通常立即生效；若不生效再：
cd ~/leap_ros_ws && colcon build --packages-select xuegecar_camera --symlink-install
```

> 💡 建议在路由器里给**主控板**和**图传板**都做 **DHCP 静态绑定**，否则重启后 IP 可能变。
> 变了也不用慌：`cam` 模式每次都会重新问一遍，`09_preflight.sh` 也会报不一致。

## 故障排查速查表

| 现象 | 最可能的原因 | 怎么解决 |
|---|---|---|
| **搜不到 `Maturo_` 热点** | 固件没烧 / 板子没上电 / 已配过网 | 回第 2 步烧录固件；已配网的板子不再发热点，需长按复位或重烧 |
| **`192.168.4.1` 报"响应时间过长"** | **连成了图传板热点**（`Maturo_CAM_...`） | 换连不带 `CAM` 的主控板热点；图传板请用 `192.168.1.88`。跑 `bash 10_diag_portal.sh` 自动判别 |
| **配网页打不开（连对了热点）** | 没拿到 IP / 热点没起 | 看 WiFi 是否显示"已连接"；`bash 10_diag_portal.sh` 查网关；重连热点 |
| **两块板子只能连上一个** | 一块无线网卡只能连一个 AP | 分开配：先配主控板（`192.168.4.1`），拔掉再配图传板（`192.168.1.88`） |
| **配网后热点不消失** | WiFi 名/密码错、路由器 5G | 重新配网；确认路由器有 **2.4GHz** |
| **白灯一直闪，热点一直在** | 没连上 WiFi | 正常＝等你配网；填错 WiFi 名/密码、或路由器只有 5G。白灯**常亮**才是连上了 |
| **红灯长亮，白灯也常亮** | 全部正常 | 红灯是**电源指示灯**（硬件直连，只表示供电正常，永远不闪）；白灯常亮＝已连上 WiFi |
| **白灯慢闪，热点也在** | 按过 BOOT 键切成 micro-ROS | 正常，跑 ROS 2 要的就是这个模式；重新上电即恢复默认 |
| **两个灯都不亮** | 没供电 | 查电池电压（≥7.4V）、电源开关、排线 |
| **`ros2 topic list` 看不到 `/scan`** | ① Agent 会话没建立（最常见）② Agent IP 填错 | 先看【终端 A】有没有 `[ OK ] 机器人已连接`；没有就**按 RESET 键**或在【终端 B】跑 `bash 05_run_robot.sh reset`。再看配网页/`/api/status` 里的 `microros_agent_ip` 是否等于你电脑 IP |
| **`/odom` 出现在列表里，但 `hz` 一直没数据** | **正常现象** | `xuegecar_bringup` 只**订阅** `/odom`（用它生成 TF），并不发布。判连线要看 `/scan` `/imu` `/battery_state` |
| **RViz 里 `LaserScan` 红字 `Status: Error`** | **Topic 是空的**（裸 `rviz2` 是空白配置） | 选中 `LaserScan` → 点 `Topic` 下拉框 → 选 `/scan`。或直接 `bash 05_run_robot.sh rviz`（会自动加载项目配置） |
| **RViz 3D 区一片空白，Global Status 报错** | `Fixed Frame` 用了还不存在的坐标系 | 跑 SLAM/导航时用 `map`；只跑核心链路（无 SLAM）时改成 `odom` 或 `base_footprint` |
| **RViz 里雷达点太小/几乎看不见** | `Size (m)` 默认 `0.01` 太小 | 选中 `LaserScan` → 把 `Size (m)` 改成 `0.02~0.03` |
| **机器人刚连上又断了 / Agent 重启后连不上** | 固件"连过就不再重连"的行为 | 必须**复位机器人**（RESET 键或 `bash 05_run_robot.sh reset`）。Agent 后起、重启、换端口之后都要复位一次 |
| **【终端 A】刷屏、卡死，滚都滚不动** | 旧脚本用 `-v6` 把 Agent 日志直接打到终端（30 秒 32MB） | 已修：日志改写到 `/tmp/leap_ros_agent.log`（默认 `-v4`）。重跑 `bash 05_run_robot.sh core` 即可 |
| **`tail -f /tmp/leap_ros_agent.log` 提示文件不存在** | Agent 不是用新版 `05_run_robot.sh` 启的 | 说明跑的是旧实例。回【终端 A】`Ctrl+C` 后重新 `bash 05_run_robot.sh core` |
| **`UDP :8888 已被占用`，但那个终端已经叉掉了** | 终端被直接关闭时 Agent 不会退出，改挂到 `systemd` 下变成**孤儿进程**（实测残留 24 分钟） | `bash 05_run_robot.sh core --force` 自动清理；或按脚本提示 `kill <PID>`。**清完记得复位机器人**（`bash 05_run_robot.sh reset`）|
| **`bash 05_run_robot.sh reset` 卡很久没输出** | 旧版扫描时没过滤 ARP 表里的 `FAILED` 条目 | 已修（实测 23 秒完成）。若仍慢，直接给 IP：`bash 05_run_robot.sh reset 192.168.x.x` |
| **Agent 一直不显示 client 连接** | 不在同一网段 / AP 隔离 | 电脑和机器人连同一路由器；关掉 AP 隔离 |
| **`/scan` 有话题但没有数据** | 雷达没接好 | 检查雷达排线插紧（主控 GPIO41 接口） |
| **socat 报 sudo 错误** | launch 里的硬编码密码 | **可忽略**（雷达走 /scan）；或跑 `06_setup_lidar_socat.sh` |
| **相机画面打不开** | ① **相机要预热 8~10 秒**，短超时会误判成流坏了 ② 配置 IP 和图传板实际 IP 不一致 | 跑 `bash 05_run_robot.sh cam`（自动问机器人要地址）；手测请用 `curl --max-time 20 http://<相机IP>:81/` |
| **点了 `2D Pose Estimate` 后地图开始抖** | **SLAM 和 Nav2(amcl) 同时在跑，两条 `map→odom` 打架**（该按钮发 `/initialpose`，gmapping 不订阅、amcl 订阅） | 只留一套：建图关 Nav2、导航先关 SLAM；`bash 12_diag_jitter.sh` 第 0b 节可自动判定 |
| **地图本身在闪/抖（不是车抖）** | `/map` 有两个发布者（gmapping 实时图 + map_server 静态图） | `ros2 topic info /map` 看 Publisher count，只留一个 |
| **车不动，但 `/cmd_vel` 有数据** | 电机线 / 电池电压不足 | 检查 M1/M2 接线、电池是否 ≥ 7.4V |
| **车走偏、方向反了** | 电机线左右插反 | 对调 M1/M2 接线，或在参数里反转 |
| **终端报 `AMENT_TRACE_SETUP_FILES`** | 手动 source 顺序问题 | 用 `05_run_robot.sh` 启动（已处理），别手写 source |
| **ROS 2 和 ESP-IDF 冲突报错** | 同一终端 source 了两者 | **分开不同终端**，别混用 |
